#696 本機測試資料準備

此文件是準備清單，尚未連線、匯出或匯入任何資料庫。實際資料庫名稱、版本、授權及資料內容需由環境管理者確認；不將連線資訊或憑證放入版本控制或 issue。

資料範圍

  • 專案設定分成 PostgreSQL main 與 datastore。文本語料程式直接使用 main；既有資料集功能及完整站台仍可能使用 datastore，不可假設只匯入主庫即可驗證全部功能。
  • 確認主庫結構、migration 歷程，以及必要的機關、科室、角色、權限、詞彙、測試提供者與會員資料。測試帳號須涵蓋資料管理者、同機關指定與非指定審核者、跨機關審核者及系統管理者。
  • 避免匯出不必要的個資、憑證、API 金鑰、連線字串或信件佇列；在提供副本前依資料管理要求處理敏感資料及關聯完整性。
  • 資料庫副本不包含實體上傳檔案或搜尋索引。文本測試應使用新建測試檔；若驗證既有 OD 的下載或搜尋，需另行確認檔案和索引的測試資料。

本機隔離與檢查

  1. 確認 Docker／PostgreSQL 可用及容器、網路與儲存位置皆屬獨立開發環境；主庫與 Datastore 的目標名稱應明確區分 testing 來源。
  2. 準備適合開發的測試資料副本，確認 PostgreSQL 與備份工具版本相容，再由負責環境的人員提供安全的匯入方式。
  3. 匯入前確認目標是空的獨立資料庫；匯入後檢查 migration 狀態、基本表與角色權限。不可對 testing 來源執行 migration 或測試寫入。
  4. 設定本機專用檔案儲存、前後臺 URL、測試登入及搜尋服務；確認寄信、排程、對外公告及外部同步不會連向真實服務。
  5. 後臺私有 npm 套件需既有 registry 存取權限；依本機環境安全地設定，不提交或分享 token。依專案 Dockerfile 使用 Node 24。
  6. 在副本確認備份與回復方式後，才執行本分支 migration；將結果及差異記錄於 #696，並執行 696-corpus-publication-integration-checklist.md。

尚待確認

  • 副本能否提供、如何去識別化，以及是否需要主庫和 Datastore 的完整資料。
  • 前臺假登入與後臺測試帳號在本機副本的設定方式；reCAPTCHA 等外部驗證如何在測試環境處理。
  • 公告和通知盤點中的正式範本，以及測試環境的安全收件方式。
  • 目前工作區 Docker Desktop WSL 整合尚未啟用；能否由使用者環境啟用或使用既有容器主機。

程式碼補充：前臺假登入僅在非 production 且 jwt.fakelogin 明確啟用時可使用，並讀取固定 ID 的會員紀錄；本機副本必須準備對應的測試會員，且不能假設此方式已涵蓋多會員或後臺角色測試。實際登入及設定尚未驗證。

後臺登入頁的測試按鈕固定使用 b103，而非正式環境且啟用 jwt.fakelogin 時的測試登入服務可依帳號名稱取得 token。多角色驗證仍需準備對應帳號、機關及權限，並在隔離環境確認實際登入流程；不得在 production 啟用此測試機制。
